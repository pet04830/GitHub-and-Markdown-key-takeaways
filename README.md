# Three ways I will use GitHub as a Technical Writer

**GitHub** is a platform for users to manage, store, and work together on projects, and this is particularly helpful for technical writing professionals working with programmer/engineering teams. Technical writers utilize GitHub to create, edit, and organize documents, including user manuals, guides, API documents, and software manuals. GitHub uses version control, thus allowing writers to observe changes, process previous versions, and co-work with developers without losing the important information. Technical writers have the option to give suggestions to developers regarding their work, as well as issue pull requests and make comments on documents. Working in GitHub helps to keep written documents informative and relevant while making technical writers an active part of the development process.

## Turning Complex Information into Easy-to-Follow Guides

As a technical writer, I will use **GitHub** to convert complex technical details into documentation that is easier for users to comprehend. For instance, if a developer develops a feature, I am able to create a user manual that explains the usage round by round. I would highlight important messages and operations in bold, while I would rely on *italics* for the special terms and use numbers to simplify complicated procedures. The technology of **Markdown** would help me ensure that the information is well-structured and does not seem confusing.

* **Bold**: Used to emphasize important information.
* *Italics* : Used to emphasize words or technical terms.
* Lists: Used to organize instructions and information clearly.

## Using GitHub Issues to Find Documentation Problems

It is possible for me to make use of **GitHub** Issues to keep tabs on the different problems pertaining to the documentation. In case a user points out that a tutorial is unclear, or a developer makes a change to the working of a feature, I can create an issue that describes the problem. The issues can further be segregated into different categories like "Needs Updating", "User Confusion", or "New Documentation".
I could also track my progress through checklists:

1. Identify the confusing section
2. Ask the developer for clarification
3. Rewrite the documentation
4. Have another person review the changes
5. Publish the updated version

This would turn **GitHub** into more than a place to store my writing, it would become a tool for managing the entire documentation process.

## Building Documentation That Works Like a Conversation
Instead of just writing about the finalized feature I will use **GitHub** to connect with developers throughout the development process. By using comments, pull requests, and discussions I will ask questions when I am confused about any technical topic and help engineers develop a clear explanation. For instance, I will be able to leave a comment like: “Could you explain what happens if this function does not work properly?” 

I will also use **Markdown** in order to give developers my feedback:

* Explain what the feature does in simple language.
* Clarify what users should do if something goes wrong.
* Add an example to show users how the feature works.
* Review the documentation with the developer before publishing.

Utilizing **GitHub** in this manner let me be a conduit between developers and users. The aim will be to ensure that the technical material is not only correct, but also comprehensible and useful for the desired audience.
